## 代码作用

这是一个 Python `for...else` 结构（pipeline.py:298, 356）。`else` 只在 `for` 循环**正常跑完（没 break）**才会触发：

- 主循环最多 10 轮（`MAX_TOOL_ROUNDS=10`，pipeline.py:260），每轮 LLM 要么给最终答案（无 `tool_calls`，触发 break），要么继续调工具
- 跑满 10 轮还在调工具 → 模型一直没收敛 → 进入 `else` 兜底
- 兜底逻辑：再发一次请求，但 `tool_choice="none"` **禁用工具**，强迫模型基于现有 `messages`（含历史工具结果）直接产出文字答案

## 影响

**正面**：
- 保证 pipeline 必定有一个文字 `msg.content` 返回，不会因循环到顶而吐 "(无回答)"
- 给 `total_input/total_output/llm_time` 累加上这次最终请求的开销，统计准确
- 防止工具调用死循环吃光预算

**代价**：
- 额外一次 LLM 调用，多一次延迟和 token 成本
- 此时 `messages` 已包含 10 轮交互，prompt 很长，单次费用不便宜
- 兜底分支里**没有** `_recorder.record_tool_call`，但这是合理的（这次没调工具）；不过最终 `msg` 也没单独打 round 标记，问答记录里这一轮的来源可能不易区分

## 幻觉风险 —— 是的，有，而且不低

主要风险点：

1. **被强行收敛**：模型本来想再调工具拿数据（说明它觉得信息还不够），却被剥夺了工具权限。它可能：
   - 基于不完整的工具结果硬编造答案
   - 重复/曲解已有工具返回的片段
   - 把"还没查到"说成"查到的结果是 X"

2. **长上下文 + 噪声**：10 轮里如果有失败的工具调用（`result.error`）或被截断的结果（pipeline.py:338-339，>4000 字符截断为 `... (截断)`），模型可能把截断处的内容脑补完整。

3. **没有 system 提示加固**：进入兜底时 system message 没变，没有像"如果信息不足请明确说明无法回答"这样的指令约束，模型默认行为是尽量给个回答 → 容易硬答。

## 改进建议（如果要做）

- 兜底时追加一条 system/user 消息，比如："基于以上已收集的信息直接作答；如果信息不足，请明确说'信息不足，无法回答'，不要编造"
- 给兜底产生的回答打个标记（如在记录里加 `truncated_by_max_rounds=True`），便于后续质量评估和样本筛选
- 监控 `_round_count == MAX_TOOL_ROUNDS-1` 时的出现频率，频繁触发说明 10 轮可能不够，或工具/prompt 设计有问题

`pipeline.py:338` 工具返回 >4000 字符就 `... (截断)`。`kingdee_describe_form` 单次 ~65KB，几乎必然被截断，模型可能因此再发一次更窄的查询，又是一轮。

## 根因（按重要性排序）

### 1. 核心问题：金蝶里根本没有"氧化铜"这个物料 —— 但模型分不清"无数据"和"出错"

`result_size=84` 实证：空结果 JSON `{"count": 0, "data": []}` 格式化后正好 30 字节，加上工具结果包裹层（roughly content 字段的 84 字节）—— **`success=1` + `result_size=84` 是"调用成功但 0 行"的固定指纹**。

`pipeline.py:334-337` 的处理：
```python
if result.error:
    content = json.dumps({"error": ...})
else:
    content = json.dumps(result.data, ...)  # → '{"count": 0, "data": []}'
```

模型拿到 `{"count": 0, "data": []}` 后没法区分这是"业务上不存在"还是"查询条件错了"，于是不停换 keyword/limit 重试。这是**无法回答类问题的典型症状**，CLAUDE.md V0.2 第 6 条说应该 `kingdee_get_wiki(topic="伪问题与数据缺口/无法回答的问题清单")` 兜底，模型没走这条路径。

### 2. 第 1 轮真正的报错没有被识别

round=1 的 `success=0` + `latency_ms=0`，几乎瞬时返回 → 不是网络/接口问题，更像是**参数校验失败或同一调用被去重/取消**（紧跟在 round=0 之后用相同参数）。模型继续把这当"重试机会"，又试了 4 次同名工具，4 次都成功但 0 行。

### 3. 路由策略与失败重试叠加

CLAUDE.md V0.2 三层路由要求：query → schema → wiki → relations。模型严格按此走（轮 3-4-7），但**主问题（查不到物料）在第 0 轮就已经定调**，后续 9 轮全部是"白干"，每多一轮都让兜底分支离触发更近。

### 4. 之前 5 次"complete" 也跑满了 10 轮

```
truncated=1, round_count=10 的总会话数=6（即所有 6 次 round_count=10 中只 1 次被标记 truncated）
```

说明此前 5 次也都是触顶 `MAX_TOOL_ROUNDS`，但**最后一轮模型自己生成了文字答案**（无 tool_calls）→ break 出循环 → `complete`。换句话说：**这个问题本来就是一个高耗轮问题，10 轮不够用，本次只是运气更差，第 10 轮还在调工具**。

content = json.dumps(result.data, ensure_ascii=False) if not isinstance(result.data, str) else result.data

**C. 轮数预警（早于触顶）**
