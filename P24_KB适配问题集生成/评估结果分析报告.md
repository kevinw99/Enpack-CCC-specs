# P24 评估结果分析报告

**日期**: 2026-04-13
**评估框架**: P21 Evaluation Harness + P24 问题集 (88题)
**评估模型**: DeepSeek-Chat / Claude Sonnet 4
**评分模型**: DeepSeek-Chat (LLM-as-Judge, 盲评)

---

## 1. 评估概述

### 1.1 目标

用 P24 生成的 88 题三类别问题集替换 P21 原有的 30 题问题集，重新评估 KB MCP 的增值效果。验证三个假设：

| 假设 | 描述 | 判定标准 |
|------|------|---------|
| H1 | KB 在覆盖范围内有显著增值 | A 类 MCP 胜率 ≥80% |
| H2 | MCP 不引入副作用 | B 类 MCP 胜率 40-60% |
| H3 | MCP 不编造 KB 未覆盖内容 | C 类 MCP 胜率 ≥30% |

### 1.2 问题集分布

| 类别 | 数量 | 预期结果 | 说明 |
|------|------|---------|------|
| A — KB独占优势 | 60 (68%) | MCP 胜 | 问题答案主要来自 KB 专有内容 |
| B — 通用知识 | 18 (20%) | 平局 | 公开行业知识可回答，KB 无显著增值 |
| C — KB未覆盖/对抗性 | 10 (11%) | MCP 平手或略输 | 故意超出 KB 覆盖范围 |

### 1.3 评估流程

```
harness.py: 每题生成 Vanilla + MCP 两份回答
    ↓
scorer.py: DeepSeek 盲评 (5维度打分 + 胜者判定)
    ↓
report.py: 分层统计 + 假设验证
```

评估中 MCP 配置的工作方式：用 VectorDB (1345 chunks) 语义搜索 KB，将 top-5 相关文档片段注入 prompt 作为上下文。

## 2. 评分 Prompt 迭代过程

评分 prompt 的设计对结果影响极大，经历了 4 个版本的迭代：

| 版本 | 核心立场 | MCP 胜 | 问题 |
|------|---------|--------|------|
| v1 | "引用来源应视为有据可查，在可信度维度给予认可" | 76 (86%) | 可信度 +1.33，过度奖励引用 |
| v2 | "仅仅引用来源不应自动加分" | 37 (42%) | 可信度 -0.50，Judge 把真实 KB 数据当幻觉 |
| v3 | "引用既不加分也不扣分" | 35 (40%) | 同 v2，准确性 -0.67，Judge 无法验证公司数据 |
| **v4** | "内部数据可能真实，不应仅因无法验证就判为编造；但也不自动加分" | **55 (62%)** | **均衡** |

### 核心发现：LLM-as-Judge 的固有偏差

DeepSeek 作为 judge 存在一个根本矛盾：
- MCP 回答引用了 KB 中的**真实公司数据**（如"2024年营收20.18亿元"）
- Judge 的训练数据中**没有这些信息**，因此倾向于判定为"编造"
- v1 通过"引用=可信"绕过了这个问题，但引入了反向偏差
- v4 通过告知 judge "这是真实公司的内部评估"来平衡两方面

### v4 评分 prompt 关键内容

```
系统提示：
- 这是一家真实公司的内部AI助手评估
- 引用内部文档的公司专有数据不应仅因无法验证就判为编造
- 也不应仅因引用了文档就自动认为信息可靠
- 综合判断信息的内在一致性和合理性

可信度维度：
- 1分：信息自相矛盾或明显违背常识
- 5分：信息准确可靠，不确定的地方诚实说明
```

## 4. 典型案例分析

### 4.1 A类复杂题：KB 增值巨大

**KB-A27: 我们的主要竞争对手有哪些？他们各自的技术路线和竞争优势是什么？**

| | Vanilla | MCP |
|---|---------|-----|
| 回答 | "请告诉我您的行业是什么" — 完全不知道公司背景，要求用户提供信息 | 列出古河电工、JX金属、三井金属等具体对手，详细对比技术路线、专利组合、Enpack 的定位优劣势 |
| 评分 | 12/25 | 22/25 |

**KB-A52: 30.89亿元投资预计多少年能收回？**

| | Vanilla | MCP |
|---|---------|-----|
| 回答 | "我需要更多信息"，给出通用公式 "投资额÷年现金流" | 引用文档中 13-17 年 (基础) / 6-8 年 (乐观) 两个预测，列出 80% 利用率、30-40% 毛利率等具体条件 |
| 评分 | 14/25 | 23/25 |

**KB-A33: 固态电池商业化对集流体供应商的影响？**

| | Vanilla | MCP |
|---|---------|-----|
| 回答 | 泛泛地说"机会与威胁并存"，建议"深入研究"、"保持联系" | 引用固态电池市场 11.8→150 亿美元增长数据、公司双轨策略、产能规划，给出分阶段行动方案 |
| 评分 | 20/25 | 25/25 |

### 4.2 B类题：Claude vanilla 过于保守

**KB-B09: IRA 对全球电池供应链有什么影响？**

| | Vanilla | MCP |
|---|---------|-----|
| 回答 | 列出"供应链重构"、"投资流向变化"等通用要点，但无具体数据 | 引用 KB 中北美产能从 100→1,200+ GWh 的数据、各州产能分布、18-24 个月设备采购周期 |
| 评分 | 19/25 | 24/25 |

B 类 MCP 胜率高 (78%) 的原因：Claude vanilla 在回答行业问题时过于保守，倾向于说"建议查阅最新报告"，而 KB 搜索意外搜到了相关的市场研究数据。

### 4.3 C类题：MCP 诚实拒答

**KB-C03: 最近3个月的客户投诉汇总**

| | Vanilla | MCP |
|---|---------|-----|
| 回答 | "我无法访问您的数据库"，给了通用分类框架 (Zendesk 等) | "知识库中投诉率、主要投诉内容均为[待收集]状态"，基于 KB 已识别的运营痛点给出建议 |
| 评分 | 21/25 (胜) | 14/25 |

此例 vanilla 胜出，因为 MCP 暴露了 KB 中的"[待收集]"模板状态，judge 认为信息空洞。这是 C 类的预期行为。

**KB-C06: 英联复合铜箔产能利用率是多少？**

| | Vanilla | MCP |
|---|---------|-----|
| 回答 | "我无法提供"，只列了影响因素的通用清单 | 虽无实际数据，但引用 KB 中 5亿㎡产能规划、5-10 条产线运营现状，推算出处于设计产能 5-10% |
| 评分 | 13/25 | 22/25 (胜) |

MCP 虽然也没有实际数据，但能基于 KB 中的间接信息做出合理推算。

## 5. 结论

### 5.1 KB MCP 的价值

1. **KB 在其覆盖范围内有显著增值**（H1）
   - Claude: A 类 92% 胜率，完全验证
   - DeepSeek: A 类 70% 胜率，有增值但不如 Claude 显著（因 DeepSeek 本身行业知识更强）

2. **KB 增值的核心维度是具体性和可操作性**，而非准确性
   - Vanilla 模型倾向于给通用框架和"建议查阅资料"
   - MCP 能给出具体的公司数据、数字、文档引用

3. **越复杂的问题，KB 增值越大**
   - Claude 复杂题 MCP 胜率 100% (20/20)
   - 复杂问题需要更多专有数据支撑分析

4. **MCP 不会编造 KB 未覆盖的内容**（H3 两个模型均 PASS）
   - C 类 40% 胜率：MCP 能诚实说明"知识库中无此数据"
   - 部分情况下 MCP 能利用 KB 间接信息做合理推断

### 5.2 模型差异

| 维度 | DeepSeek | Claude Sonnet 4 |
|------|----------|-----------------|
| Vanilla 行业知识 | 较强（锂电池领域） | 较弱，过于保守 |
| KB 增值幅度 | 适中 (+0.34 综合分差) | 显著 (+0.84 综合分差) |
| 成本 | $0.06 / 88 题 | $1.95 / 88 题 |
| H2 表现 | PASS (50%) — 理想 | FAIL (78%) — vanilla 太弱 |

### 5.3 评估方法论的经验教训

1. **LLM-as-Judge 的 prompt 设计至关重要** — 可信度维度的评分标准差异可以让结果从 86% 翻转到 40%
2. **Judge 无法验证公司专有数据** — 必须在 prompt 中提供适当的背景信息
3. **DeepSeek 自评偏差** — 同一模型既生成回答又当 judge 可能存在风格偏好，理想情况下应使用不同模型评分
4. **B 类问题设计** — Claude 的 B 类 FAIL 暴露了问题：KB 搜索仍能找到相关内容，说明 B 类问题需要与 KB 内容完全无关才能真正充当对照组

### 5.4 后续建议

1. 使用 Claude 作为 judge 交叉验证（待 Anthropic API 网络问题解决后）
2. 考虑优化 B 类问题，选择与复合箔/英联完全无关的通用科学问题
3. 考虑在 operations 域补充实际运营数据（目前多为模板），以提升该域 MCP 表现

### 6.2 技术问题记录

**Anthropic API ConnectTimeout 问题**：
- 原因：macOS 上 Python asyncio 的 DNS 解析与系统 DNS 行为不一致。系统 DNS (223.6.6.6) 将 `api.anthropic.com` 解析为 VPN 拦截地址 `198.18.0.4`，async httpx 通过该地址连接超时。
- 解决方案：将 `AsyncAnthropic` 改为同步 `Anthropic` + `asyncio.to_thread()`，绕过 async DNS 解析问题。
- 文件：`rd_ai_tools/common/llm_client.py`
