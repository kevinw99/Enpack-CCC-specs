## 28 题为什么不敏感

**P20S 的价值维度**：
1. 消除字段幻觉（Q013 式错误）
2. 提供关联 JOIN 路径
3. 提供状态枚举语义
4. 暴露公司自定义字段（`F_BDK_*`）

**P20T 的价值维度**：
5. 公司私有业务规则（"已审核"在本公司什么时候落库？）
6. 伪问题识别（L5 那 18 题）
7. 多步分析（采购成本趋势 + 供应商对比）

如果 28 题里大部分是**单表简单查询**（如"列出物料"），模型不需要 P20S 就能写对 → 加 P20S 无可测量的增益。如果其中没有**伪问题**，加 P20T 的拒答能力也不可见。

评估集是否能暴露变化，取决于"**题目是否命中这些价值维度**"，而不是"是否依赖 ERP 数据"。

## 降本建议：分层指标

不要只看 overall score，至少分开报：

```
每题三个信号：
1. field_validity_rate   (字段是否真实存在 — P20S 直接指标)
2. factual_correctness   (数据是否对 — 传统评分)
3. business_grounding    (业务判断是否正确 — P20T 指标)
```

**field_validity_rate 是廉价的先导指标** — 不用跑完整 LLM-as-Judge 评分，只要检查选的字段 key 是否在 schema 里存在（我在 `regression.py` 里已经实现了）。这个指标可以在 P20T 落地之前就先跑 P20S 的增量，得到一个可量化的"P20S 让字段幻觉率从 X% 降到 Y%"数字。

这样评估是渐进式的，不用憋到最后一次性跑。

## 什么是 "turn"

一个 **turn = LLM 一次"思考 → 决定调哪个工具 → 拿到结果"的完整回合**。

整个流程是循环：

```
Turn 1:  LLM 看问题 → 决定调 kingdee_get_schema("BD_Supplier")
         → MCP 返回 schema 内容
Turn 2:  LLM 看 schema → 决定调 kingdee_get_wiki("财务/应收")
         → MCP 返回 wiki 内容
Turn 3:  LLM 看所有上下文 → 决定调 query_bills(...)
         → MCP 返回数据行
Turn 4:  LLM 看数据 → 决定不再调工具，输出最终 JSON 答案
```

每个 turn 是一次 LLM API 调用 + 可能一次 MCP 工具调用。turn 越多：
- 越慢（每 turn 3-6 秒）
- 越贵（累积 token 消耗；上下文越来越长）
- 越容易跑偏（LLM 可能无限循环探索）

## MAX_TURNS 是硬上限

`MAX_TURNS = 8` 意思是：**LLM 最多有 8 次机会调工具**；到第 8 轮仍没输出最终答案，runner 就强制它"别再调工具了，立刻总结"。

### v1 的问题（为什么 100% 题撞顶）

LLM 在 T1/T2 下的典型用 turn 模式：

```
Turn 1: kingdee_get_schema("BD_Supplier")      ← 探索
Turn 2: kingdee_get_schema("BD_Material")      ← 继续探索
Turn 3: kingdee_list_cached_schemas()          ← 看看还有什么
Turn 4: kingdee_get_schema("BD_Supplier") 又一次  ← ❌ 重复调！
Turn 5: kingdee_describe_form("BD_Supplier")   ← 同一信息第三种方式
Turn 6: kingdee_search_forms_online("...")     ← 还不放心
Turn 7: query_bills(...)                        ← 终于开始查数据
Turn 8: ⚠️ 撞顶，强制总结（经常只查到一半）
```

前 6 轮都在"确认字段存在"，真正 **query 数据的只有 1-2 轮**，数据不够 → 答案质量低 → factual/validity 崩。

这就是为什么 v1 报告里 `avg_turns=8.0`、`max_hit_rate=100%`，且**采纳了工具但没产生价值**。

## v2 的 P0 修复怎么解决

| 修复 | 作用 |
|------|------|
| MAX_TURNS 8→12 | 多给 4 轮给"真正查数据"用 |
| prompt "同 form_id 只调一次 get_schema" | 砍掉 Turn 4 那种重复浪费 |
| prompt "第 9 轮必须收尾" | 明示 LLM 预算意识 |
| prompt "search_forms_online 不许连调超 1 次" | 砍掉 Turn 5-6 那种反复搜索 |
| prompt "伪问题硬约束" | 防止 LLM 学会"调 wiki → 宣称伪问题"逃避（v1 T2 下 L8 全崩的根因）|

**类比**：v1 LLM 像个焦虑的实习生，反复查手册确认格式才敢动笔，30 分钟才写一句话；v2 是同一个实习生被经理盯着说"5 分钟写完初稿，细节边做边查"。

- **诊断难**：轮数太多 tool_calls log 难读
- **12 是试探值**：够收尾、不够失控；跑完看结果再决定要不要再提高

## 1. 为什么 LLM 忽略 prompt 规则

LLM prompt 是**概率性约束**不是**硬性强制**：

- **prompt 是建议，不是代码**：LLM 读完规则后，在具体情景下会综合权衡"先验行为模式 vs 当前规则"。当 LLM 内部判断"找不到这个表单"的焦虑够强，它会忽略规则继续搜索。
- **训练先验根深蒂固**：`search_forms_online` 这种"找不到就再搜一次"是 LLM 从预训练里学来的直觉；我的一行 prompt 胜不过千万次训练样本。
- **规则打架**：我同时写了"优先行动""不要连续搜索""判伪问题要严"——LLM 读完不知道哪条权重高，它会按自己的直觉拿捏。
- **长 prompt 注意力衰减**：我的 system prompt 现在约 500 字，埋在中段的规则命中率本来就低。

### 真正有效的强制办法（代码层、不靠 prompt）

| 办法 | 效果 | 代价 |
|------|------|------|
| Runner 检测到连续相同 tool 调用 → **拒绝/强制跳过** | 硬阻断 | 需改 mcp_runner.py 的 tool call 循环 |
| 直接从工具白名单里**移除** `kingdee_search_forms_online` | 完全杜绝 | 牺牲偶然有用的场景 |
| 给每个工具设**独立调用 quota**（如 search ≤ 1 次、get_schema ≤ 3 次） | 精细控制 | 实现稍复杂 |
| Wiki 的"伪问题目录"在系统里**只读一次**，读完的 topic 记黑名单 | 防止 L8 T2 类误用 | 需状态记录 |

## 2. 完整跑完 vs 中途打断

**我当前的策略**：让一轮完整跑完再评估。

### 为什么这样

- **T0 已经跑完**（41 分钟，46/46），现在打断只能让 T1/T2 白费 — 没有 T1/T2 就没法算 delta
- **早期信号有欺骗性**：v1 时 L1/L2 看起来还行，是 L8 T2 才爆（wiki 误用），只看前半段不会发现
- **分层聚合是 P26 的核心价值**：L1→L8 各层归因只有全数据齐了才说得清
- **成本低**：一轮 ~2h + $1 左右，不值得用复杂的中断逻辑省

### 什么情况下我会中途打断

- **崩溃级信号**：连续 5 题返回 error（而非仅质量差）
- **明显回归**：T0 跑出来 validity <0.3（比 v1 的 0.637 差太多）— 说明 prompt 改出 bug
- **API 失败率爆表**：DeepSeek 连续超时 / 限流

判断标准：**"修改的方向没错"就跑完；"修改本身引入了 bug"才中断重来**。

### 更聪明的做法（以后可以加）

在 runner 里加**在线健康检查**：每跑完 10 题就自检一次均分，如果明显偏离预期区间，自动早停并写一条 "EARLY_ABORT: reason=..." 到日志。现在没做是因为：
- 判断阈值需要多轮数据才能定
- 加上检查点会让 runner 代码复杂起来，现在 v1→v2 差异大，还在探索期

### 你的直觉哪个更好

**跑完再评估** 在"探索期 / 每轮差异大 / 每轮成本低" 这三条成立时更好 — 就是现在的情况。

**早停迭代** 在"优化期 / 每轮改动小 / 每轮成本高" 时更好 — 比如以后调某个具体参数想 5-10 次，每次只跑 T1，成本压到 20min/轮。

我现在是前者。如果到了 v4/v5 改动粒度变细，我会切到后者模式。
