## Assessment: This is already managed well

The setup is actually clean and intentional:

1. **`specs/`** (with `s`) is the **base-owned template directory**. It only contains `00_template/` and `README.md`. These come from `ai-project-base` via `git merge base/main`. You should never put project specs here.

2. **`规格/`** is the **project-owned spec directory**. This is where all real P## specs live. The Chinese naming is a deliberate project convention.

3. **The entity registry handles all three** — look at `entity_registry.py:24`:
   ```python
   _SPEC_DIRS = ["规格", "spec", "specs"]
   ```
   It scans all three directories and discovers specs from whichever exists. It also scans `RESTRICTED/规格/` for restricted specs. So regardless of which naming convention you use, the session history tool finds everything.

4. **No duplication** — `specs/` has only templates (which the scanner skips via `_SKIP_NAMES` → `"00_template"`), and `规格/` has only actual specs. They serve completely different purposes.

### Why `specs/` doesn't contain project specs

Because base owns it. If you put project specs in `specs/`, the next `git merge base/main` could cause conflicts if base ever adds more template files. Keeping project specs in `规格/` gives clean separation.

### The only minor inconsistency

The `specs/README.md` from base says "Create directory: `##_descriptive-name/`" as if you'd put specs inside `specs/`, but in this project you actually put them in `规格/`. This is fine — the README is a generic template. Each project adapts the convention to its own directory.

**Bottom line: no action needed.** The current split (`specs/` = base template, `规格/` = project specs) is the intended design and matches the openclaw pattern (`specs/` = base template, `spec/` = project specs).
