## 1. 系统架构

### 1.1 设计原则

**最大化利用 Claude 原生能力，最小化代码开发**：
- **对话模式（默认）**：Claude Code 直接使用工具（Read/Glob/Edit）完成全部流程，**无需编写任何 Python 代码，无额外费用**
- **API 自动化模式（保留）**：仅在未来大规模批量处理时启用，需要额外 API 费用

## 2. 对话模式详细设计

对话模式是 v2.1 的核心模式，**无需编写任何代码**，完全由 Claude Code 在对话中完成。

### 2.1 完整处理流程

```
用户: 处理 上传文档/MA设备技术资料/蒸发舟使用手册.pdf，注入到知识库

Claude Code 执行:

1. [Read 工具] 读取源文档
   └─ PDF 自动转为文本

2. [Claude 直接处理] 提取结构化信息
   └─ 从文本中识别参数、步骤、设备、表格
   └─ 自动跳过目录、乱码、页眉页脚

3. [Claude 直接处理] 整理成中间文档
   └─ 按类型分组，格式化为 Markdown
   └─ 展示给用户

4. [提示用户] 审查中间文档
   └─ [直接注入] / [我先看看] / [跳过此阶段以提高效率]

5. [Glob 工具] 扫描知识库文件列表
   └─ 知识库/ + private/知识库/

6. [Read 工具] 读取相关 KB 文件章节结构
   └─ 识别 ## 标题和 [待补充] 占位符

7. [Claude 直接处理] 决定注入目标
   └─ 哪个文件、哪个章节、替换还是追加

8. [展示匹配方案] 等待用户确认

9. [Edit 工具] 执行注入
   └─ 整块注入，添加来源注释
```

### 2.2 分块读取策略

对话模式下，Claude Code 使用 Bash + Python 库读取二进制文档（PDF/DOCX/XLSX），并根据文档大小自动分块。

#### 2.2.1 分块阈值矩阵

| 格式 | 分块单位 | 直接读取阈值 | 每块大小 | 使用工具 |
|------|---------|-------------|---------|---------|
| **PDF** | 页 | ≤40 页 | 40 页/块 | PyPDF2 (文本) / Read (视觉) |
| **DOCX** | 段落/章节 | ≤400 段落 | 按 Heading 分章节 | python-docx |
| **XLSX** | 行 (per sheet) | ≤1000 行 | 1000 行/块 | openpyxl |
| **PPTX** | - | 无限制 | 直接读取 | Read 工具 / python-pptx |
| **TXT/MD** | 行 | ≤2000 行 | 2000 行/块 | Read 工具 |

#### 2.2.2 PDF 分块流程

```
1. 获取页数: PyPDF2.PdfReader → len(pages)
2. 判断分块:
   - ≤40 页 → 一次性提取全部页面文本
   - >40 页 → 按 40 页一组分块, pages[0:40], pages[40:80], ...
3. 图片型 PDF 检测:
   - PyPDF2 提取文本为空或乱码 → 标记为 ⚠️ 图片型
   - 提示: 使用 Read 工具视觉读取, 或建议 OCR
```

#### 2.2.3 DOCX 分块流程

```
1. 加载文档: Document('file.docx')
2. 统计段落数: len(doc.paragraphs)
3. 判断分块:
   - ≤200 段落 → 一次性读取全部段落 + 表格
   - >200 段落 → 按 Heading 样式切分章节, 逐章节处理
4. 表格独立提取: 遍历 doc.tables, 按行读取
```

#### 2.2.4 XLSX 分块流程

```
1. 加载工作簿: openpyxl.load_workbook(read_only=True)
2. 遍历每个 sheet:
   a. 获取行数: ws.max_row
   b. 判断分块:
      - ≤500 行 → 一次性读取全部数据
      - >500 行 → 按 500 行一组: iter_rows(min_row=1, max_row=500), ...
3. 输出格式: 每行用 ' | ' 分隔单元格值
```

#### 2.2.5 图片型 PDF 处理

部分 PDF（如扫描件、厂商手册）为纯图片，PyPDF2 无法提取有效文本。

**检测方法**：
- PyPDF2 提取结果为空字符串
- 提取结果为逐字符分散（如 `B o r o n  N i t r i d e`），非正常连续文本

**处理方式**：
- 标记为 `⚠️ 图片型 PDF`，在中间文档中注明
- 建议用户使用 Read 工具进行视觉读取（Claude 多模态能力）
- 或提示使用外部 OCR 工具处理

### 2.3 提取指南

Claude 在对话中提取信息时遵循以下规则：

**提取类型**：
- **工艺参数**：名称-值-单位三元组（如 `蒸发速度: 0.4~0.5 g/min·cm²`）
- **操作步骤**：有序流程，保持逻辑连贯
- **设备信息**：名称、型号、厂商、规格参数
- **数据表格**：保留表头和结构

**过滤规则**：
- 跳过目录条目（如 `蒸发舟的安装 --- 01`）
- 跳过页眉页脚、页码
- 跳过无法理解的乱码
- 参数名应简洁（`蒸发速度` 而非 `蒸发舟的蒸发速度为`）

**输出格式**（中间文档）：

```markdown
## 工艺参数

| 参数名 | 值 | 单位 | 来源 |
|--------|---|------|------|
| 蒸发速度 | 0.4~0.5 | g/min·cm² | 蒸发舟使用手册.pdf |

## 操作步骤

### 蒸发舟预热流程
1. 电压由 0 缓慢升至 2.5V（不超过 3V）
2. 观察舟表面，此阶段应呈暗黑色
3. ...

<!-- 来源: 蒸发舟使用手册.pdf -->

## 设备信息

### 蒸发舟
- **规格**: 130×30×9 mm
- **厂商**: 山东鹏创

<!-- 来源: 蒸发舟使用手册.pdf -->
```

### 2.4 匹配指南

Claude 决定注入目标时遵循以下规则：

**目标选择优先级**：
1. 有 `[待补充]` 占位符的章节（最优先）
2. 章节标题与内容类型匹配（如 `工艺参数` → 参数内容）
3. 文件路径与主题相关（如 `01_制造工艺/MA蒸镀工艺.md` → MA 蒸镀内容）

**动作类型**：
- `replace_placeholder`: 目标章节有 `[待补充]` 时替换
- `append`: 目标章节无占位符时追加到末尾
- `new_section`: 目标章节不存在时创建

**注入格式**：
```markdown
## 原有章节标题

原有内容...

### 新增内容

新注入的内容

<!-- 来源: 蒸发舟使用手册.pdf -->
<!-- 注入时间: 2026-02-05 -->
```

### 2.5 冲突解决策略

当待注入内容与 KB 现有内容存在冲突时，**必须由人工判断**，不同情况采用不同处理方式。

#### 冲突类型

| 冲突类型 | 示例 | 严重性 | 处理原则 |
|---------|------|--------|---------|
| **参数值冲突** | KB: "蒸发舟寿命 8-10h" vs 新源: "6-8h" | 高 | 人工判断哪个来源更可靠 |
| **步骤/流程冲突** | KB: 4阶段加热 vs 新源: 3阶段加热 | 高 | 人工判断是否为不同场景/版本 |
| **来源/厂商冲突** | KB: 厂商A数据 vs 新源: 厂商B数据 | 中 | 可能两者都正确，需标注来源 |
| **重复内容** | 相同信息已存在，措辞略有不同 | 低 | 跳过或合并 |
| **补充关系** | 新内容是现有内容的细化/扩展 | 无冲突 | 直接追加 |

#### 对话模式冲突处理流程

```
1. 提取新内容
2. 读取目标 KB 章节的现有内容
3. Claude 对比新旧内容，识别潜在冲突
4. 如有冲突:
   ┌─────────────────────────────────────────────────────┐
   │ ⚠️ 检测到内容冲突                                    │
   │                                                     │
   │ 参数: 蒸发舟寿命                                     │
   │ KB 现有值: 8-10h (来源: 内部实测, 2026-01)           │
   │ 新源文档值: 6-8h (来源: 厂商手册, 2016)              │
   │                                                     │
   │ 请选择处理方式:                                      │
   │ [1] 保留 KB 现有值                                   │
   │ [2] 替换为新值                                       │
   │ [3] 保留两者并标注差异                               │
   │ [4] 跳过此项                                         │
   └─────────────────────────────────────────────────────┘
5. 用户选择后执行
```

#### 冲突标注格式（保留两者时）

```markdown
#### 蒸发舟寿命

| 来源 | 值 | 说明 |
|------|-----|------|
| 内部实测 (2026-01) | 8-10h | 基于 EWG-165 设备实际使用数据 |
| 厂商手册 (2016) | 6-8h | 山东鹏程标称值 |

> **注**: 内部实测数据与厂商标称值存在差异，实际使用以内部实测为准。
```

#### 自动化模式冲突处理

自动化模式下，检测到冲突时**暂停处理**，输出冲突报告供人工审查：

```
[冲突报告] 文件: 蒸发舟使用手册.pdf
─────────────────────────────────────
冲突 #1:
  参数: 蒸发舟寿命
  现有: 8-10h
  新值: 6-8h
  状态: ⏸️ 待人工确认

冲突 #2:
  ...

请运行 --resolve-conflicts 进入交互式冲突解决。
```

### 3.2 LLMExtractor（自动化模式核心）

```python
class LLMExtractor:
    """调用 Claude API 提取 + 匹配 + 生成注入方案"""

    def __init__(self, model: str = "claude-opus-4-5-20251101"):
        self.client = anthropic.Anthropic()  # 从环境变量读取 API key
        self.model = model

    def process_document(self, file_path: str, kb_summary: str) -> list[MatchPlan]:
        """
        一次 API 调用完成：读取文档 → 提取 → 匹配 → 返回注入方案

        Args:
            file_path: 源文档路径
            kb_summary: KB 文件列表和章节结构摘要

        Returns:
            注入方案列表
        """
        # 读取文档内容
        content = self._read_document(file_path)

        # 构建 prompt（提取 + 匹配一体化）
        prompt = f"""你是技术文档处理专家。请完成以下任务：

1. 从文档中提取有价值的技术信息：
   - 工艺参数（名称-值-单位）
   - 操作步骤（有序流程）
   - 设备信息（名称、型号、规格）
   - 数据表格

2. 跳过目录条目、页眉页脚、乱码

3. 决定每部分内容应注入到哪个知识库文件的哪个章节

源文档: {file_path}
---
{content}
---

知识库结构：
{kb_summary}

以 JSON 格式返回注入方案：
```json
{{
  "extractions_summary": "提取内容概述",
  "matches": [
    {{
      "content": "要注入的完整内容（Markdown格式）",
      "target_file": "目标KB文件路径",
      "target_section": "目标章节",
      "action": "append|replace_placeholder|new_section",
      "reason": "匹配理由"
    }}
  ]
}}
```"""

        response = self._call_api(prompt)
        return self._parse_response(response)
```

## 7. 未来计划：动态 Token 预算（待实施）

> 以下方案在启用自动化批量处理后实施，当前仅保留为规划文档。

### 7.1 背景分析

v2.5 将分块常量翻倍后，token 利用率从 8-18% 提升到 ~16-36%。但仍有以下问题：

- **固定分块大小无法适配内容密度**：稀疏叙述文本 40 页可能只用 12K tokens，密集参数表 40 页可能用 31K tokens
- **KB Summary 固定开销大**：每次 API 调用重复发送 ~11K tokens 的知识库结构
- **不同内容类型的最优块大小不同**：参数表需要精细提取（小块），操作流程需要完整上下文（大块）

### 7.2 Token 消耗现状（v2.5）

```
总 Input Token 预算: 200,000 tokens
固定开销（每次 API 调用）:
  - System Prompt:       ~300 tokens
  - KB Summary:        ~11,000 tokens
  - 跨块上下文 (5块):    ~450 tokens
  - 模板文字:             ~150 tokens
  合计固定:            ~12,000 tokens

可用于内容:           ~188,000 tokens

各格式当前占比（v2.5 翻倍后）:
  PDF 40页 (500字/页): ~13,000 tokens → 总 ~25K → 占 200K 的 12.5%
  DOCX 100段落章节:    ~7,800 tokens → 总 ~20K → 占 200K 的 10%
  XLSX 1000行x10列:   ~48,000 tokens → 总 ~60K → 占 200K 的 30%
```

### 7.3 动态 Token 预算方案

**核心思路**：不再固定页数/行数，改为按 token 预算动态合并原子块。

```
格式感知原子块 (页/章节/行)
        ↓
估算每块 token 数 (本地计算，0 API 开销)
        ↓
贪心合并相邻块，直到触及 token 预算
但不跨越语义边界 (不同 Heading / 不同 Sheet)
        ↓
送入 API 处理
```

**双档 token 预算**（根据内容密度自动切换）：

| 档位 | Token 预算 | 触发条件 | 占 200K |
|------|-----------|---------|---------|
| 标准档 | 100K tokens | 默认（叙述/流程/设备描述） | 50% |
| 精密档 | 50K tokens | 检测到高密度参数表（`|` 占比 >5% 或连续数值行 >20） | 25% |

**密度检测**（本地计算，0 token 开销）：
- 扫描块内容中 `|` 字符占比（markdown 表格特征）
- 统计连续包含数字的行数（参数密集特征）
- 超过阈值 → 降到精密档

**Prompt 增强**（大块时追加，~35 tokens）：
- 大块（>50K tokens）时追加指示："请先扫描全部内容，列出所有可提取项，然后逐项输出完整内容。不要遗漏任何参数。"
- 此指示强制 LLM "两步走"（先概览再逐条），对抗注意力稀释

### 7.4 预期收益

| 指标 | v2.5（当前翻倍） | 动态预算（未来） |
|------|----------------|---------------|
| API 调用次数 (100页 PDF) | ~3 次 | ~1-2 次 |
| 固定开销重复 | 3×12K = 36K tokens | 1-2×12K = 12-24K tokens |
| 跨页关联质量 | 好（40页内直接关联） | 更好（50-100页直接关联） |
| 参数提取精度 | 好 | 好（精密档保持小块） |
| 适配性 | 固定，不区分内容 | 自适应内容密度 |

- 已完成 v2.5 常量翻倍并验证质量无退化
- 已有足够的真实文档处理数据来验证效果
