## 自动化模式（保留）

自动化模式有两层分块，均基于**字节长度**，定义在 [settings.py](源代码/chunked_processor/config/settings.py)：

### 第一层：ChunkSplitter（文本通用分块）

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `chunk_size` | **20,480 字节 (20KB)** | 单块最大字节数 |
| `chunk_overlap` | **500 字符** | 块间重叠，防止信息截断 |

这是 [chunk_splitter.py](源代码/chunked_processor/file_layer/chunk_splitter.py) 使用的配置，按 UTF-8 字节计算，在自然边界（段落、句号、换行）处切分。

### 第二层：LLM 大块处理（送入 API 的块）

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `llm_chunk_size` | **150,000 字节 (150KB)** | 单次 API 调用最大输入内容 |
| `large_chunk_size` | **102,400 字节 (100KB)** | 大文档分块时每块大小 |
| `large_chunk_overlap` | **2,000 字符** | 大块间重叠 |
| `llm_max_tokens` | **32,768 tokens** | API 输出 token 上限 |
| `llm_temperature` | **0.0** | 确定性输出 |

逻辑流程（[llm_extractor.py:151](源代码/chunked_processor/extraction/llm_extractor.py#L151)）：
1. 文档内容 UTF-8 字节 > `llm_chunk_size`（150KB）→ 启用分块
2. 按 `large_chunk_size`（100KB/块）+ `large_chunk_overlap`（2000字符重叠）切分
3. 每块独立调用 API，`max_tokens=32768` 限制输出

## 对话模式 vs 自动化模式

| 维度 | 对话模式 | 自动化模式 | 优势方 |
|------|---------|-----------|--------|
| **成本** | 无额外费用（Claude Code 订阅内） | 需要 Anthropic API 费用 | 对话模式 |
| **代码维护** | 零代码，无维护负担 | 需维护 Python 代码 + 依赖 | 对话模式 |
| **模型能力** | Opus 4.6（最新） | Opus 4.5（settings.py 写死） | 对话模式 |
| **上下文窗口** | Claude Code 完整上下文 | 受 `llm_chunk_size` 150KB 限制 | 对话模式 |
| **分块精度** | 按文档语义单位（页/章节/行） | 按字节硬切（100KB），可能截断语义 | 对话模式 |
| **冲突处理** | 实时交互，逐条确认 | 暂停+输出报告，需二次介入 | 对话模式 |
| **批量能力** | 1~20 个文档，逐个处理 | 50+ 文档，glob 批量 + 断点续传 | 自动化模式 |
| **无人值守** | 不支持，需人在回路 | 支持，可后台运行 | 自动化模式 |
| **可重复性** | 依赖对话上下文，难以复现 | 代码确定性执行，结果可审计 | 自动化模式 |
| **进度持久化** | 对话断开则丢失 | ProgressManager 持久化，断点续传 | 自动化模式 |

## 核心判断

**对话模式更好**，原因：

1. **分块质量更高** — 按页/章节/行这类语义单位分块，远优于按字节硬切。自动化模式的 `large_chunk_size=100KB` 按字符位置切分（虽然会找句子边界），但无法感知文档结构（如 PDF 的页、DOCX 的 Heading），可能将一个完整表格或步骤拆到两个 API 调用里。

2. **提取质量更高** — 对话模式下 Claude 可以看到完整的对话上下文（之前处理过的块），能做跨块去重和关联。自动化模式每个块是独立 API 调用，块与块之间无共享上下文，只靠 2000 字符重叠来弥补。

3. **成本为零** — 这是最实际的因素。自动化模式每次 API 调用都计费，Opus 模型单价高，处理 50 个文档的费用不可忽视。

4. **灵活性** — 遇到图片型 PDF、格式异常、语义模糊等情况，对话模式可以实时调整策略（比如切换到视觉读取），自动化模式只能报错或跳过。

## 自动化模式的唯一优势场景

当你需要**一次性处理 50+ 个文档且不需要人工审查每一条注入**时，自动化模式的批量能力和断点续传才有意义。但从你目前的使用模式看（逐批处理技术资料子文件夹），对话模式完全够用。

## 建议

保持现有策略不变：**对话模式为默认，自动化模式保留但不投入维护**。如果未来确实出现需要无人值守批量处理几百个文档的场景，再启用自动化模式，届时也应该把模型升级到最新版本。

### 12:31 - 调整后的的优缺点是什么

**Prompt:**

**Result:**
好问题，加大分块不是无条件的好事。逐条分析：

## 加大分块的优点

**1. 减少 API 调用次数 → 省钱**

固定开销（System Prompt + KB Summary）每次调用都要重复发送：

| 场景 | 当前 (20页/块) | 调整后 (60页/块) |
|------|--------------|----------------|
| 100 页 PDF | 5 次调用 × ~12K 开销 = **60K tokens 浪费** | 2 次调用 × ~12K = **24K tokens 浪费** |

KB Summary 占 ~11K tokens，这是每次必须重发的。调用次数减少 = 直接省钱。

**2. 更大的上下文 → 更好的跨页关联**

例如：第 5 页提到"蒸发舟型号 BN-130"，第 35 页才给出该型号的详细参数。当前 20 页/块会分到两个独立调用，靠跨块摘要传递（有损）。60 页/块可能在同一次调用中看到两者，关联质量更高。

**3. 减少对跨块上下文机制的依赖**

跨块上下文本质是"有损压缩"——只传摘要，不传原文。块越大，需要跨块传递的信息越少，信息保真度越高。

---

## 加大分块的缺点

**1. LLM "注意力稀释" → 可能漏提细节**

这是最关键的风险。当输入内容太多时，LLM 可能：
- 对密集的参数表"一扫而过"，漏掉个别参数
- 倾向于提取"大块的、明显的"信息，忽略夹在长文中的小细节
- 输出更粗糙的摘要，而非逐条精确提取

**2. 单次失败的代价更大**

| | 20 页/块 | 60 页/块 |
|---|---------|---------|
| API 超时/报错 | 损失 20 页，重试成本低 | 损失 60 页，重试成本 3x |
| 输出截断 | 影响少量内容 | 可能丢失更多提取结果 |

**3. PDF 页面密度差异大 → 不可预测**

不是所有页面都一样：
- 纯文字说明页：~300 字/页 → 60 页 ≈ 12K tokens
- 密集参数表：~800 字/页 → 60 页 ≈ 31K tokens  
- 图文混合手册：差异可能 3-5 倍

固定 60 页/块的实际 token 数波动很大，不如按 **token 数量** 来动态切分更可靠。

**4. DOCX 合并不同章节 → 语义混乱**

DOCX 当前按 Heading 切分是有语义意义的——每块是一个完整章节。如果只是提高阈值到 600 段落，小文档可以整体处理（好），但不影响大文档的按章节切分逻辑（中性）。

---

## 更好的策略：动态 token 预算

与其固定调大页数/行数，不如让分块策略**按 token 预算动态合并**：

```
目标: 每次 API 调用的内容占 ~120K tokens (200K 的 60%)
留 ~12K 给固定开销，~68K 给安全余量
```

| 格式 | 当前策略 | 优化策略 |
|------|---------|---------|
| PDF | 固定 20 页/块 | 按页读取，累积到 ~120K tokens 为止 |
| DOCX | 按 Heading 切 | 按 Heading 切，然后将相邻小章节**合并**到 ~120K |
| XLSX | 固定 500 行/块 | 按行累积到 ~120K tokens 为止 |

这样：
- 稀疏的 PDF 可以一次读 100+ 页
- 密集的参数表 PDF 可能只读 40 页
- 自动适配，不需要人工调参


这两条曲线交叉的点就是最优解。但这个交叉点**不是固定的**，它取决于内容类型。

## 不同内容类型的"最优块大小"不同

| 内容类型 | 跨页关联需求 | 注意力稀释风险 | 最优策略 |
|---------|------------|-------------|---------|
| 操作步骤/流程说明 | 高（前后步骤有依赖） | 低（叙述性文本，LLM 擅长） | **放大**，越多越好 |

| 纯表格 Excel | 低（行间独立） | 高（每行都要精确提取） | 偏小即可 |

所以真正的答案不是"固定一个大块大小"，而是**根据内容密度动态调整**。

核心思路：**用 token 预算做上限，用内容密度做调节**。

```

                    │  格式感知原子块       │
                    │  (页/章节/行)         │
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │  估算每块 token 数    │
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │  贪心合并相邻块       │
                    │  直到触及 token 预算   │
                    │  但不跨越语义边界     │
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │  送入 API 处理        │
                    └──────────────────────┘
```

**关键的平衡机制在于 token 预算不是一个固定数字，而是两档：**

| 档位 | Token 预算 | 触发条件 | 占 200K |

| **精密档** | 50K tokens | 检测到高密度参数表 | 25% |

- 100 页叙述型 PDF → 合并成 2 块（每块 ~50 页），跨页关联最大化
- 100 页参数表 PDF → 合并成 4 块（每块 ~25 页），提取精度保持

- ≤40 页：直接用 `python3 + PyPDF2` 一次性提取全部文本
- \>40 页：按 40 页一组分块读取，逐块提取
  ```bash
  python3 -c "
  import PyPDF2
  r = PyPDF2.PdfReader('文件路径')
  for p in r.pages[起始:结束]:
      print(p.extract_text() or '')
  "
  ```
- ⚠️ **图片型 PDF 检测**：如果 PyPDF2 提取的文本为空或明显为逐字符乱码（如每个字符间有空格），

**DOCX 文件**：
- 用 Bash + python-docx 读取：
  ```bash
  python3 -c "
  from docx import Document
  doc = Document('文件路径')
  for p in doc.paragraphs: print(p.text)
  for t in doc.tables:
      for row in t.rows: print(' | '.join(c.text for c in row.cells))
  "
  ```
- 段落数 ≤400：一次性读取全部内容
- 段落数 >400：按 Heading 样式分章节读取，每次处理一个章节

**XLSX 文件**：
- 先用 Bash 获取各 sheet 的行数：
  ```bash
  python3 -c "
  import openpyxl
  wb = openpyxl.load_workbook('文件路径', read_only=True)
  for name in wb.sheetnames:
      ws = wb[name]
      print(f'{name}: {ws.max_row} rows x {ws.max_column} cols')
  "
  ```
- 每个 sheet 独立处理：
  - ≤1000 行：一次性读取全部数据
  - \>1000 行：按 1000 行一组分块读取
  ```bash
  python3 -c "
  import openpyxl
  wb = openpyxl.load_workbook('文件路径', read_only=True)
  ws = wb['Sheet名']
  for row in ws.iter_rows(min_row=起始行, max_row=结束行, values_only=True):
      print(' | '.join(str(c) if c is not None else '' for c in row))
  "
  ```

**PPTX 文件**：

**TXT / MD 文件**：

2. **"动态调整"需要定义触发条件和流程**——不是随时可以改，否则KPI就没有约束力。建议明确：谁有权申请调整、需要什么审批、调整后如何记录
3. **案例用真实场景**——你们现在实际在做MA转量产、产品改善，直接用这些做案例最有说服力
