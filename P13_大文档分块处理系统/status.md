## 版本历史

### v1.0（2026-02-03 ~ 2026-02-05）— 已废弃

正则提取 + 规则评分架构。实施完成 Phase 1-6，Phase 7 实际验证暴露严重质量问题。

**v1 实施成果**：
- 200+ 测试通过
- 文件处理层：6 种格式读取器 + 智能分块
- 提取层：4 个正则提取器
- 预处理层：去重 + 分组 + 预分类
- 匹配层：KB 索引 + 批量匹配 + 排序
- 注入层：文件更新 + 新文件生成
- 支撑层：进度管理 + 日志 + 报告
- 整理层（两阶段扩展）：主题检测 + 中间文档 + 章节解析 + 章节匹配

**v1 暴露问题**：

| 问题 | 严重性 | 表现 |
|------|--------|------|
| PDF 文本乱码 | 严重 | 多列排版导致断句混排，如 `●降低蒸镀均匀性。发速率的方法是错误的` |
| 目录误提取 | 严重 | TOC 条目被识别为操作步骤（354 条"步骤"大多是 TOC） |
| 参数名碎片化 | 严重 | 整句话作为参数名（如 `蒸发舟的蒸发速度为`） |
| 去重不足 | 中等 | 同一章节内容重复 3-4 次 |
| 匹配错误 | 严重 | 真空系统操作步骤匹配到 MC 复合铜箔制造工艺 |
| 设备信息碎片化 | 严重 | 设备规格完全不可读 |

**v1 决策**：正则提取器能力上限太低，改为 LLM 驱动。

### v2.0（2026-02-05 ~）— 当前

LLM 驱动提取 + LLM 匹配架构。

## 决策记录

| 日期 | 决策 | 理由 |
|------|------|------|
| 2026-02-03 | v1: 正则提取 + 规则评分 | 初始方案，无需 API |
| 2026-02-03 | v1: 两阶段处理架构 | 分离提取和匹配 |
| 2026-02-05 | **废弃 v1 正则提取** | 实测质量严重不足 |
| 2026-02-05 | **v2: LLM 驱动提取** | 用户选择方向 B（LLM 提取），使用 Opus 模型 |
| 2026-02-05 | **v2: 保留两阶段 + 中间文档** | 用户要求保留人工审查检查点 |
| 2026-02-05 | **v2: 中间文档可选跳过** | 系统在合适时机提醒用户是否跳过以提高效率 |
| 2026-02-05 | **v2: 先对话验证再建自动化** | 两者结合，降低风险 |
| 2026-02-05 | **v2: LLM 匹配替代规则评分** | LLM 理解语义，比规则评分更准确 |
| 2026-02-06 | **LLM 为默认模式** | 用户明确要求不使用正则等低质量方式 |
| 2026-02-06 | **一次 API 调用完成提取+匹配** | 简化流程，降低复杂度 |
| 2026-02-06 | **32K output tokens, 150KB chunk** | 匹配 Phase B 对话模式验证的配置 |
| 2026-02-07 | **对话模式设为默认，API 自动化保留** | 对话模式无额外费用且已验证有效；API 模式需额外付费，保留供大规模批量处理 |
