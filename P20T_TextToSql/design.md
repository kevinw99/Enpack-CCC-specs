# Design: P20T TextToSql

## Approach

采用**两层架构**：语义层（LLM Wiki）负责"知道该查什么"，执行层（MCP Server）负责"去查并返回数据"。
两层通过 CLAUDE.md 中的路由规则连接，AI 先判断问题类型，再决定走哪条路径。

```
用户提问
    │
    ▼
┌─────────────────────────────┐
│       问题路由（CLAUDE.md）  │
│  "是什么/为什么" → Wiki      │
│  "查数据/统计"  → MCP        │
└──────┬──────────────┬───────┘
       │              │
       ▼              ▼
┌────────────┐  ┌─────────────────┐
│  LLM Wiki  │  │   MCP Server    │
│  语义层    │  │   执行层        │
│            │  │                 │
│ - 业务术语 │  │ - kingdee_query │
│ - 表字段   │  │ - futures_spot  │
│ - 枚举值   │  │ - 期货分析      │
│ - 伪问题   │  │                 │
│ - 数据流   │  │                 │
└─────┬──────┘  └────────┬────────┘
      │                  │
      ▼                  ▼
┌─────────────────────────────┐
│         LLM 整合回答         │
└─────────────────────────────┘
```

### Wiki 页面格式规范

每个 Wiki 页面遵循统一结构：

```markdown
# [业务主题]

## 业务背景
[这个模块是做什么的，业务流程简述]

## 关键表单（Form ID）
| 表单名称 | Form ID | 说明 |
|---------|---------|------|
| 采购订单 | PUR_PurchaseOrder | ... |

## 关键字段说明
| 字段标识 | 字段名称 | 类型 | 枚举值说明 |
|---------|---------|------|-----------|
| FDocumentStatus | 单据状态 | 枚举 | A=暂存, B=审核中, C=已审核 |

## 数据流路径
[用文字或图描述数据从哪里来、到哪里去]

## 常见查询模式
[给出典型查询的字段组合和过滤条件]

## 已知陷阱 ⚠️
[记录 AI 曾经踩过的坑，防止重犯]

## 相关问题
- Q-XXX: [问题标题]
```

## Key Decisions

### Decision 1: Wiki 而非扩大 `问题库回答指南.md`
**理由**：单文件随内容增长，AI 每次要读整个文件。Wiki 按主题分页，AI 只需检索相关页面，上下文消耗可控。

### Decision 2: 不引入向量数据库
**理由**：当前文档量（10-15 页）不需要向量检索。直接在 CLAUDE.md 中配置路由规则，AI 根据问题关键词判断读哪个 Wiki 页面，足够应对当前规模。

### Decision 3: 伪问题显式写入 Wiki
**理由**：避免 AI 对无数据的问题编造答案。明确告诉 AI"Q007 采购合同：ERP 中无此数据"，比让 AI 自己去查然后幻觉要可靠得多。

### Decision 4: 枚举值必须业务人员确认
**理由**：Q013 的教训——AI 自己推断状态值 B/C 含义，结果搞错了。所有枚举值必须来自业务人员确认，在 Wiki 中标注来源。

### Decision 5: 知识沉淀采用人工审核后追加
**理由**：自动追加风险高（AI 可能把错误答案也追加进去）。每次 AI 回答被业务人员确认正确后，手动将关键知识点追加到对应 Wiki 页面。

## Technical Details

### 路由规则（CLAUDE.md 更新）

```markdown
## 问题路由规则

回答问题前，先判断问题类型：

1. **定义/解释类**（"是什么"、"为什么"、"有什么区别"）
   → 先查 wiki/ 目录下对应主题页面

2. **数据查询类**（"有多少"、"哪些"、"趋势"、"对比"）
   → 先查 wiki/ 确认表单和字段，再用 MCP 工具查询

3. **无法回答类**（伪问题/数据缺口）
   → 查 wiki/伪问题与数据缺口/无法回答的问题清单.md，直接告知用户

## Wiki 检索方式
- 采购相关 → wiki/采购/
- 销售/应收 → wiki/销售/
- 生产/良率 → wiki/生产/
- 库存/物料 → wiki/库存/
- 财务/成本 → wiki/财务/
- 资产 → wiki/固定资产/
```

### 与现有 CLAUDE.md 的关系

现有 `CLAUDE.md` 已有"写答案前必须执行的步骤"规则，Wiki 路由规则作为**前置步骤**插入：

```
0. 查 Wiki 确认业务语义（新增）
1. 用 kingdee_describe_form 确认表单字段存在（现有）
2. 查询至少一批真实数据（现有）
...
```

## Alternative Approaches

### 方案 A: 继续扩大 `问题库回答指南.md`（当前 V0.1）
- **优点**: 零改造成本，已经在用
- **缺点**: 上下文消耗随内容增长，越来越难维护
- **结论**: 短期可用，长期不可持续

### 方案 B: Vanna（Text2SQL + RAG）
- **优点**: 自动化程度高，不依赖人工维护
- **缺点**: 需要完整 DDL（目前没有），需要额外基础设施，2-3 周验证周期
- **结论**: 作为 V1.0 后的演进方向，当前阶段过重

### 方案 C: LLM Wiki（本方案）
- **优点**: 零基础设施，人工可读可编辑，可快速迭代
- **缺点**: 仍需人工维护，不能完全自动化
- **结论**: 当前阶段最合适，1 周内可验证

## Risk Mitigation

| 风险 | 缓解策略 |
|------|---------|
| 业务人员不配合确认枚举值 | 优先处理高频问题（Q001-Q013），逐步扩展 |
| Wiki 内容与 ERP 实际不符 | 每个字段说明标注"来源：业务人员确认/AI 推断⚠️" |
| AI 忽略 Wiki 直接查 ERP | 在 CLAUDE.md 中将 Wiki 检索设为强制前置步骤 |
| Wiki 页面过多导致 AI 不知道查哪个 | README.md 维护清晰的主题索引 |
| 知识沉淀不及时 | 每次业务人员确认答案后，当场追加到 Wiki |
