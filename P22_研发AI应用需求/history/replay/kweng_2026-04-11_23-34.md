## P11 是什么、能干什么

P11（`源代码/experiment_analyzer/`）是一个**已实现到 Phase 6** 的 Python 库，提供以下能力：

| 模块 | 能做什么 | 关键文件 |
|-----|---------|---------|
| **data/** | 从 CSV/Excel/Markdown 加载实验数据、验证、清洗 | `loader.py`, `validator.py`, `cleaner.py` |
| **analysis/** | 描述性统计、相关性分析、趋势分析、异常检测 | `descriptive.py`, `correlation.py`, `trends.py`, `anomaly.py` |
| **models/** | 线性/Ridge/Lasso/随机森林/XGBoost 回归建模、交叉验证、特征重要性、SHAP | `regression.py`, `features.py`, `evaluation.py` |

| **models/optimizer.py** | 单目标/多目标参数优化 | `optimizer.py`, `multi_objective.py` |
| **reports/** | 生成 Markdown/PDF 报告 | `generators.py`, `exporters.py` |
| **visualization/** | 静态 + 交互式图表（热力图、响应面、残差图） | `static_charts.py`, `interactive_charts.py` |

**但 P11 有一个核心前提**：它需要**已有的实验数据**。没数据就啥也干不了。

## 具体的代码级协同点

R22 的 `p11_bridge.py` 调用 P11 的接口：

```python
# R22 中 reasoning/p11_bridge.py 的协同逻辑

from experiment_analyzer.models.regression import ModelFactory
from experiment_analyzer.models.features import FeatureEngineer
from experiment_analyzer.models.persistence import ModelPersistence

def get_p11_feature_importance(problem_type: str) -> dict | None:
    """尝试从 P11 已训练模型中获取特征重要性"""
    
    # 1. 查找 P11 是否有与此问题相关的已训练模型
    persistence = ModelPersistence(model_dir="models/saved/")
    models = persistence.list_versions()
    
    relevant = [m for m in models if problem_type in m.tags]
    if not relevant:
        return None  # 无相关模型，R22 纯靠 KB
    
    # 2. 加载最新模型，提取特征重要性
    model = persistence.load(relevant[-1].model_id)
    importance = model.feature_importances_  # 随机森林/XGBoost 自带
    
    # 3. 返回给 R22 的 global_ranker 做融合
    return {
        "source": "P11_model",
        "model_id": relevant[-1].model_id,
        "r2": relevant[-1].metrics["r2"],
        "feature_importance": importance  # {"走膜速度": 0.28, "真空度": 0.35, ...}
    }
```

### 03:46 - what is DOE

**Prompt:**
> what is DOE

**Result:**
DOE = **Design of Experiments**（实验设计），是统计学中用来系统地规划实验的方法论。

核心问题：当你有 N 个因子，每个因子有 2-3 个水平（高/低），全部组合会爆炸式增长（如 24 因子 × 2 水平 = 2²⁴ = **1600 万种**组合）。DOE 的目的就是用**数学方法选出最少的实验组合**，同时还能得到有统计意义的结论。

R22 代码中用到的几种 DOE 方法：

| 方法 | 适用场景 | 例子 |
|-----|---------|------|
| **全因子** (Full Factorial) | 因子少 (≤4) | 3 因子 × 2 水平 = 8 次 |
| **Plackett-Burman** | 筛选阶段 (5-11 因子) | 11 因子只要 **12 次**，快速排除不重要的 |
| **部分因子** (Fractional Factorial) | 中等规模 (12-15 因子) | 牺牲高阶交互信息，换取实验次数大幅减少 |
| **两阶段** | 因子多 (16+) | 先 PB 筛出 5-6 个主因子，再 RSM 精细优化 |

**在 R22 的语境下**：步院长的 24 因子如果全部做正交实验要 100+ 次。R22 先用 AI+KB 把 24 个筛到 5-6 个主因子，然后用 DOE 方法（比如 PB）设计 12 次实验就够了。这就是"压缩比 88%"的意思。

### 阶段 1: 问题生成（带标签）

我们标注每个问题的：
- 类别（A/B/C）
- 生成方法（①-⑥）
- 预期结果（MCP优/持平/MCP劣）

**这些标签不进入评估流程**，只保存在元数据文件中。

### 阶段 2: 盲评（P21 评估框架）

评委（LLM-as-Judge）收到的信息**只有**：
```
问题: "xxx"

评委**不知道**：

- 这个问题属于 A/B/C 哪个类别
- 这个问题的"预期结果"是什么

评分完成后，合并元数据，做分组统计：

```
总结果: MCP胜率 = X%

## 关于对抗性问题（方法⑥）

对抗性问题的目的不是"证明MCP差"，而是**压力测试**。具体来说：

- **过时信息题**：KB 中有旧数据，而 Claude 训练数据可能有更新的 → 测试 MCP 是否盲目引用过时信息
- **KB 矛盾题**：不同文档对同一问题说法不同 → 测试 MCP 是否能识别矛盾
- **KB 边缘覆盖题**：KB 只有间接相关的内容 → 测试 MCP 是否过度推断

这类题数量应少（5-8题），用于发现系统弱点，不用于计算总胜率。

## VectorDB 是什么？

VectorDB 是 **P20 (MCP KB Server)** 项目的核心组件，在 2026-03-08 由 commit `c0ddf4c` 引入。它是一个**基于 SQLite 的向量数据库**，用于存储 KB 文档的语义嵌入向量，让 MCP 服务器能够对用户问题做**语义搜索**（而不仅是关键词匹配）。

### 数据流（从文档到搜索）

```
知识库/ + 研究/ 目录下的 47 个 Markdown 文件
    ↓  scanner.py — 发现文件
    ↓  parser.py  — 按标题拆分为 Section
    ↓  chunker.py — 大段落再切为 ≤800 token 的 Chunk
    ↓  embedder.py — 用 paraphrase-multilingual-MiniLM-L12-v2 生成 384 维向量
    ↓
embeddings.db (SQLite, 5.1 MB, 1345 个 chunk)
    ↓
search.py — 用户提问 → 生成向量 → 余弦相似度匹配 → 返回最相关的文档片段
```

### 关键文件

| 文件 | 作用 |
|------|------|
| `src/store/vector_db.py` | VectorDB 类定义，存储/查询向量 |
| `src/indexer/scanner.py` | 扫描 `知识库/` 和 `研究/` 目录 |
| `src/indexer/parser.py` | 解析 Markdown，按标题拆分 |
| `src/indexer/chunker.py` | 将大段文本切成 ≤800 token 的块 |
| `src/indexer/embedder.py` | 用本地 sentence-transformers 模型生成嵌入 |
| `src/tools/search.py` | 搜索接口：语义搜索 + 关键词回退 |
| `data/embeddings.db` | SQLite 数据库文件（1345 chunks） |

### 它在评估中的角色

在 `harness.py` 的评估流程中，**Config B (MCP-augmented)** 的工作方式就是：
1. 拿到用户问题
2. 调用 `search_knowledge_base(question, db=db, max_results=5)` — 从 VectorDB 中找到最相关的 5 个文档片段
3. 把这些片段注入到 prompt 中作为上下文
4. 让 DeepSeek 基于这些上下文回答

所以 VectorDB 就是 MCP 服务器的"记忆"——它不是一个外部服务，而是一个**本地 SQLite 文件**，用 `python -m src.cli index` 命令从 KB 文档一次性生成。这个组件从 P20 Phase 1 就有了，是 KB MCP 服务器的基础设施。

### 12:50 - what is this " 4. Ingest BOS designer exports (if ever...

**Prompt:**
> what is this " 4. Ingest BOS designer exports (if ever provided)"

**Result:**
BOS 是金蝶云星空的**业务对象设计器**（Business Object Studio），是金蝶给客户用来自定义/查看业务对象（表单、字段、流程）的内置工具。从 BOS 设计器可以**导出** `.bos` 或 `.xml` 文件，内含表单的完整元数据定义（字段、控件、关联、业务规则等）。

## 在 P20S 里的角色

P20S 的三通道抽取方案里：

| 通道 | 来源 | 状态 |
|------|------|------|
| **Channel A** (官方 API) | `QueryBusinessInfo` REST API | ✅ 主通道，已跑通 32 张表 |
| **Channel B** (BOS 导出) | 金蝶 BOS 设计器导出的 `.bos`/`.xml` 文件 | ⏳ 解析器代码就绪，**等用户导出文件** |
| **Channel C** (LLM 兜底) | DeepSeek 推断 | ✅ 代码就绪，当前未触发（Channel A 已覆盖 100% 中文名） |

代码在 `源代码/mcp-kingdee-server/schema_extractor/channels/bos_parser.py`，支持 `parse_bos_file` / `parse_bos_dir`。

## 为什么可能"永远不 ingest"

Channel B 的价值场景是：**Channel A 覆盖不到的自定义业务对象**。但当前发现：
- Channel A 已经把 32 张表的字段中文名覆盖到 100%
- 公司暂未大量使用 BOS 自定义业务对象（或还没发现 Channel A 漏了什么）

所以 Channel B 是**保留的备胎**——如果未来：
- 发现某些公司自定义表 Channel A 查不到完整字段
- 或者想补 `F_BDK_*` 类自定义字段的详细元数据

那时让管理员在 BOS 设计器里导出对应业务对象，放进 `./bos_exports/` 目录，跑 `python -m schema_extractor --bos-dir ./bos_exports/` 即可激活。

## 要不要现在做

**不必**，除非：
1. 你发现 schema 里有字段缺中文名或缺类型信息（目前没有）
2. 你想把公司所有自定义业务对象（包括只在 BOS 里定义、没通过 API 暴露完整信息的）纳入 schema

所以我在刚才的清单里把它标为"**if ever provided**"——它是 P20S 实现上已 ready 但业务上可能**永远不需要激活**的一条通道。把它当作功能已完成、数据输入可选即可。

## 1. 如果 MCP 是被 Claude Desktop 或某个 Claude Code 会话挂载的

**做法**：去那个客户端重启 MCP 连接。

- **Claude Desktop**: 退出并重开 App（Cmd+Q → 重新打开）。重开后它会用新代码重新 spawn `python -m src.server`。

可以这样确认有没有残留进程：
```bash
ps aux | grep "src.server" | grep -v grep
```
通常看到的每一行都是某个客户端的子进程，杀掉它那个客户端会断连。

## 3. 如果只是要跑 P23 / P26 评估
